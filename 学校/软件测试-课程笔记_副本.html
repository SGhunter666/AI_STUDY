第一讲回答一个元问题：软件质量保证（SQA）在整个工程过程中扮演什么角色？答案以「五个基本工程问题」为骨架展开。

1.1工程过程中的质量

工程过程关注三件事：产品适用（fit for purpose）、过程可复现、过程可反思改进。落到软件上就是一对经典口号：

  • Validation（确认）——build the right thing：满足真实使用需要；
  • Verification（验证）——build the thing right：构建出的东西符合你的意图（规格）。

软件深嵌于组织与人们的生活，需求持续变化，因此过程必须响应式：Agile、DevOps、持续集成/部署（CI/CD）。SQA 越来越深地嵌入工程全过程——质量缺陷发现得越晚，修复成本越高。两种典型嵌入实践：

  • 测试驱动开发（TDD）：测试（大致）就是规格说明；
  • DevOps：用运行数据持续确认需求、发现需求变化、识别质量问题。

案例：Proto-AirBnB 的身份验证

早期用户群彼此高度信任（沙发客）；扩张到更大人群后诈骗上升 → 用运行数据做 validation，发现缺失的需求「用户必须被准确识别」→ 开发规格与测试 → 部署新版 → 运行数据显示诈骗下降。闭环：需求识别 → 测试构造 → 已验证产品 → 部署并采集运行数据。

课堂提问 · WOOCOLAP

"What sorts of problems arise from uploading passport images?"（要求用户上传护照图像并核验，会带来哪些问题？）

隐私与数据泄露风险、身份盗用、核验服务的可用性与误判、各国法律差异——一个好的功能需求可能引入新的质量属性要求（安全、隐私、合规）。

1.2软件为何难测：挑战清单

  • 利益相关者众多且需求冲突（同一系统对不同人群意味着不同期望）；
  • 依赖不可靠的基础设施：库、操作系统、通信链路随时可能在脚下变化；
  • 复杂且可被利用的错误：缓冲区溢出、数组差一错误（如 UoE ISG 邮件事故）；
  • 开放性：面对广泛的潜在用户与滥用者——服务大部分时间正常，却可能因依赖服务故障、DoS 攻击或 SQL 注入而失效。
考点

物理蕴含 ≠ 软件蕴含：电梯安全载重 1000 kg ⇒ 任何更小载荷都安全；但软件「对输入 x 正确」不蕴含「对任何更简单的输入正确」。软件的正确性没有这种单调性，这是测试不能「举一反三」的根本原因。

新技术是双刃剑：NL/AI 模型能减少一类录入错误，但带来过度依赖或训练数据偏见等新问题；机器学习引入大量伦理问题；设计不良的 web 服务易受资源类攻击。

1.3五个基本工程问题（全课骨架）

Five Basic Engineering Questions
问题核心回答
Q1 · SQA 在开发过程中的角色？从项目发起到退役全程参与：可行性研究阶段就要做风险分析、各阶段质量度量、演进评估、质量活动成本估算；世界在变 → 规格在变 → 质量必须持续维护。
Q2 · 如何在众多技术中选择？没有单一技术适用于所有目的。按「对不同特征的有效性 / 在项目不同时点的适用性 / 目的差异 / 成本与保证的权衡」选择。例：航空标准要求故障率低于 10-9/飞行小时——关键特征必须投入高资源。
Q3 · 产品「就绪（ready）」意味着什么？fit for purpose：故障链 fault→error（错误状态）→failure；规格常含可度量的依赖性属性（availability、MTBF、reliability）。DevOps 下「通过对应全部需求的测试集」即就绪。
Q4 · 演化中如何维持质量？QA 机制随规格持续更新；QA 机制在一定程度上「就是」文档，甚至可用于证明合规。
Q5 · 过程本身如何改进？若多个项目的产品都不达标：可能是规格→QA 技术的翻译有缺陷、QA 过程实施有问题、或资源不足；同时应消除浪费（重复、高资源技术用在低资源够用的地方）。

依赖性的三种度量（Dependability Metrics）

TERM · 术语
Availability / MTBF / Reliability
可用性：以运行时间 vs 停机时间衡量服务质量；平均无故障时间 MTBF：两次故障间的平均时间；可靠性：所有尝试操作中成功完成的比例（正确性的统计近似，100% 可靠 = 正确）。
考点 · 可靠性取决于度量单位

Web 应用用户需 50 次交互才到信用卡扣款，前 49 步永远完美，但一半的扣款金额错误：按交互计只有 1/100 失败 → 99% 可靠；按会话计只有 50% 可靠。「系统的可靠性是多少」必须先问「以什么为单位」。

DevOps 过程改进的四步循环

① 监控（异常报告+行为数据）→② 分析定位反复出现的异常→③ 数据不足以定位？改进监控与分析→④ 实施过程改进并回验历史案例

实例：监控发现 SQL 注入尝试 → 分析找出可能丢数据的具体情形 → 行动计划：标记易受注入的组件，强制系统级 SQL 注入测试。

1.4小结与速记

SQA 的三大目标：改进软件产品、评估软件产品质量、改进质量过程本身。需要组合多种技术；选择取决于组织与应用领域；成本效益取决于技术能否随产品演化复用；规划与监控是评估与精化质量过程的必要手段。

2.1Validation vs Verification（正式版）

经典 V 模型中的验证与确认活动：左侧自顶向下是规格与设计的分解（实际需求→系统规格→子系统设计→单元规格），右侧自底向上是实现与集成（单元→子系统→系统集成→交付包）。横向配对的活动依次为模块测试、集成测试、系统测试、用户验收（α/β 测试）；左侧竖向的 Review/Analysis 保证规格本身的质量。图源：Lecture 02, slide 6 · Pezzè & Young
  • Validation：软件系统满足用户的真实需要吗？（把技术系统连接到利益相关者的世界；含可用性测试、用户反馈）
  • Verification：软件系统满足需求规格吗？（把技术系统连接到或松或严的规格陈述；含测试、审查、静态分析）
考点 · 验证还是确认取决于规格本身

电梯需求「按下 i 层请求按钮后，可用电梯须在 soon 内到达」——不可验证（但可确认）；改为「30 秒内到达」——可验证。不可度量的形容词（快、友好、健壮）让验证退化为确认。改写需求时注意 30 秒在高峰期可能物理上不可达——可验证性有时要付出过度承诺的代价。

2.2你不可能总是得到想要的：不可判定性

理想中的判定器：对性质（Property）与程序（Program）给出确定的 Pass/Fail 判定（Decision），且该判定由一个可靠的过程（Procedure）自动执行。但正确性性质是不可判定（undecidable）的——停机问题几乎可以嵌入任何感兴趣的性质中。

有时可以得到：限制性质与程序的形式后可以找到判定过程（某些领域存在这样的限制）。例如 SPARK Ada 禁止无界循环与异常处理——异常处理会引入大量过程间控制流路径，形式验证需要沿所有路径追踪性质，没有大量人工工作无法精确完成。限制语言，换来可判定。

两种「不精确」：得到你需要的

Inaccuracy — 测试与分析的互补不精确性
类型含义对应技术
乐观不精确
optimistic		可能放过一些并不满足性质的程序（不能检出所有违规）测试——通过 ≠ 正确
悲观不精确
pessimistic		即使程序满足性质，也不保证接受它（可能误报）自动程序分析——报警 ≠ 有错

第三条路：简化性质（simplified properties），降低性质的自由度使其可检查。

TERM · 术语（高频考点）
Safe / Sound / Complete
Safe（安全）：无乐观不精确——只接受正确的程序；Sound（可靠）：分析程序 P 关于公式 F，仅当 P 确实满足 F 时才返回 true（真报警必真，可能有漏报）；Complete（完备）：只要 P 确实满足 F 就总是返回 true（无漏报，可能有误报）。Sound + Complete 同时成立 = 精确判定。
考点

记忆锚点：Sound = 不说谎（说的都真）；Complete = 不漏报（真的都说）。测试是 neither sound nor complete；多数静态分析 sound 但不 complete；工业分析工具常「宁可误报」换取 soundness 的子集（safe approximations）。

3.1三大通用工程原则

原则含义例子
Partition
划分		分而治之，且保证组件间交互简单结构化与功能性测试选择准则都靠划分输入空间驱动采样

可见性		让信息（至少对测试者/开发者）可及，能判断「做得怎么样」选简单/标准的内部数据格式便于单元测试（如用好的 JSON 编辑器）

反馈		用经验调优开发过程TDD 中测试驱动开发；检查清单来自历史错误
考点 · 可见性 Visibility ≠ 可观察性 Observability

可见性是过程级概念：X-visibility = 判断「我们在 X 上进展如何」的能力（进度可见性、质量可见性）；最大挑战是早期评估——在规格与设计阶段就判断产品质量。相关但不同：可观察性是程序/系统级概念。

Feedback 的双面性：项目间学习最好在开发相似产品时发生；过去经验也可能妨碍解决新问题（过度聚焦上次的惨痛教训）。

3.2三大 A&T 专属原则

TERM · 术语
Sensitivity 敏感性
好的测试选择准则应当「敏感」：无论为验证某需求选中哪些具体测试，结果都应一致。可靠准则（reliable criterion）：程序在一个被选测试上失败 ⟺ 在所有被选测试上失败——「宁可每次都失败，也不要偶尔失败」。反例：系统因固定存储区过小而失败，某准则选出的测试数据有的溢出有的不溢出 → 违反敏感性；修复：把「数据量」本身作为分类维度，保证同类的测试行为一致。
TERM · 术语
Redundancy / Diversity 冗余与多样性
用独立的冗余检查更早、更高效地捕获特定故障，即「把意图显式化」：静态类型检查之于动态类型检查；需求规格的确认之于最终软件的确认；测试与代码内断言常常搭配使用以增加信心。
TERM · 术语
Restriction 限制/简化
通过限制编码方式或修改需求（或两者）把难题变易题。弱化规格可能更易检查：一般性地证明指针使用正确不可能，但「Java 指针先初始化后使用」易于强制；强化规格也可能更易检查：动态类型语言中运行期类型错误一般不可判定排除，但静态类型语言的更强约束轻松可查。
考点 · 弱规格易查 & 强规格易查

两条方向相反却都成立的例子必须记牢：指针正确性（不可判定）→「先初始化后用」（弱化，可查）；动态类型错误（不可判定）→ 静态类型系统（强化，可查）。限制既可放松也可收紧规格，关键是被查性质的自由度下降。

Partition 在验证中的应用

硬测试/验证问题可通过对输入空间的适当划分处理：结构化与功能性测试选择准则识别代码或规格的划分（划分驱动输入空间采样）；验证技术按特征折叠输入空间，把同质数据分组确定划分。

3.3小结与速记

MEMO · 六原则总表
Sensitivity 敏感性宁可每次都失败，不要有时失败（reliable criteria）。
Redundancy 冗余静态类型、需求确认、断言——显式化意图，早发现。
Restriction 限制限制编码或改需求，把不可解变成可解。
Partition 划分分而治之，划分驱动采样（后续 EP/组合测试的理论根）。
Visibility 可见性判断进展的能力；最难在早期（规格/设计阶段）。
Feedback 反馈检查清单、错误分类学、设计指南——经验制度化。

4.1质量过程与权衡

依赖性不是整机的单一属性——通话/紧急呼叫（emergency call）与基带软件需要高依赖性，而相册滤镜不需要。按特征讨论依赖性，而不是按产品。

质量过程的三大性质

  • Completeness 完整性：对每类重要故障都规划了合适的检测活动；
  • Timeliness 及时性：故障在高杠杆点（尽可能早）被发现；
  • Cost-effectiveness 成本效益：按成本与效果选择活动——成本要在整个开发周期与产品寿命上考量，主导因素通常是活动在多次变更周期中重复执行的成本。

过程可见性：能回答「我们的进度与计划相比如何」。若不进行最终测试就无法对质量建立强信心，则可见性不足。做法：尽早设计测试用例（不是 just-in-time）；对代码前的制品用分析技术；使用代理度量（proxy measures）——设计检查发现的故障数不是可靠性的真实度量，但可作为早期质量警示指标。

4.2质量目标与依赖性家族

  • 过程质量（可见性…）与产品质量；后者分内部质量（可维护性…）与外部质量；
  • 外部质量再分：有用性（usability、performance、security、portability、interoperability）与依赖性（correctness、reliability、safety、robustness）。
Dependability 四姊妹
性质定义
Correctness 正确性程序与规格一致；对非平凡系统很少可行
Reliability 可靠性对某「行为单位」正确运行的似然性；相对规格与使用剖面；正确性的统计近似
Safety 安全性预防危害（hazards）
Robustness 健壮性极端条件下的可接受（降级）行为

交通灯案例：正确性/可靠性 = 按正确模式与中央调度放行；健壮性/安全性 = 尽可能提供降级功能、绝不亮冲突绿灯——闪黄灯好过没有灯，没有灯好过冲突的绿灯。

依赖性质量的关系（Venn 图）：Reliable 但 not correct——故障很少发生；Correct 但 not safe——规格本身不充分（做得对的东西本身是错的）；Safe 但 not robust——可能发生烦人的故障；Robust 但 not safe——可能发生灾难性故障（不崩溃地做坏事最危险）。图源：Lecture 04, slide 19 · Pezzè & Young

考点 · 激励机制如何毁掉项目（Case A / B）

25.3两个核心过程模型

测试管理过程（29119-2）：测试策略与规划 →（产出测试计划）→ 测试监控与控制 →（测试结果）→ 测试完成 →（测试完成报告）；监控反馈「测试计划更新」，向上游发出「测试状态报告」。图源：Lecture 25, slide 7
动态测试过程：测试设计与实现 →（测试规格）→ 测试执行；并行的「测试环境与数据管理」→（环境就绪报告）→ 执行；发现失效 → 测试事件报告 → 回到执行复测。图源：Lecture 25, slide 8

过程的实例化（instantiation）：标准给出的是通用过程模板——通用「测试管理过程」按项目实例化为「项目测试管理过程」，它 manage 着验收/系统/集成测试过程；通用「动态测试过程」实例化为各模块的组件测试过程……同一个抽象过程在不同层级反复落地。

项目中的测试：项目管理过程与测试管理过程双向交互——下行：控制指令 + 项目计划；上行：完成报告 + 测试状态报告。测试不是孤岛，而是嵌入项目管理的受控子过程。

20.2对中间产物做验证

质量规划的关键原则：检测修复成本随「故障引入→检测」的时间差增长（完美无缺则时间差为零）。因此高效的质量计划包含一组匹配的中间 V&V 活动，在重要故障引入后短时间内发现大部分（资源有限 → 必须聚焦重要故障）；V&V 步骤取决于中间工作产品及其预期缺陷。对中间产物的三类验证：

任务进度与关键路径

任务进度起初基于策略与过往经验，随过程推进把大任务拆成子任务并精化，包含质量活动之间及其与开发活动之间的依赖。调度准则：稳定的工作节奏与持续评估而不拖延开发；活动尽早排；提高过程可见性。

TERM · 核心定义
Critical Path / Critical Dependence
关键路径：必须顺序完成、总时长最长的活动链。关键依赖：关键路径上的任务被紧接着排在另一关键任务之后。对策：把关键任务及其依赖任务尽早排（留出时差）；分解关键路径上的任务，把能提前做的子任务拆出来先做。

资源受限的改进版：把「设计子系统/系统测试」从关键路径上拆出来，与「编码与集成」并行，关键路径上只剩测试的执行；用户文档也提前并行。图源：Lecture 20, slides 25–27

20.5过程监控与改进：ODC 与 RCA

过程监控要尽早发现与计划的偏差并纠正——前提是计划现实、组织良好、有清晰无歧义的里程碑与准则。过程可见到什么程度，就能监控到什么程度。汇总数据要「按类比评估」：

按类比评估汇总数据：横轴构建号、纵轴故障数，按严重度分级。预期形态：中期达峰后逐级下降、Critical 先归零。若曲线不达峰（测试不足）或后段不降（修复验证失败）→ 过程出了问题，这正是「类比」的诊断价值。图源：Lecture 20, slide 42
TERM · 核心定义
Orthogonal Defect Classification（ODC）
正交缺陷分类：为超大项目设计的精确分类模式，把海量细节蒸馏成可管理信息。两步——故障分类（检出时记录：暴露故障的活动、触发器、对客户的影响；修复时记录：修复目标、故障类型、来源 in-house/库/外购/外包、代码年龄 新/旧/重写/再修复）＋故障分析（看分布随时间/活动的变化）。

ODC 触发器（按活动分组）

活动触发器
评审 / 代码检视设计一致性、逻辑/流程、向后兼容、内部文档、横向兼容
功能（黑盒）测试覆盖、变体、顺序、交互
结构（白盒）测试简单路径、复杂路径
系统测试并发、负载/压力、语言依赖、恢复/异常、副作用、启动/重启、罕见情形、硬件/软件配置、受阻测试
影响（impact）可安装性、可用性、完整性/安全、标准、性能、可靠性、维护、可访问性、可维护性、能力、迁移、需求、文档

ODC 故障分析四例（判断「过程是否正常」）

  • 故障类型 × 活动分布：算法故障主要应由单元测试发现——若单元期占比异常小、集成期异常大 → 单元测试设计不良 / 集成测试没聚焦接口故障；
  • 触发器 × 时间分布（现场测试）：简单用法对应故障应早现、复杂用法晚现、新故障揭示率渐近下降——若晚期仍大量涌现「简单用法」故障 → 样本不代表用户群；持续增长 → 系统测试可能失败了；
  • 代码年龄分布：故障应集中在新代码与重写代码——移植后「基代码」故障增多 → 可移植性测试不足；
  • 故障类别 × 时间：缺失型（missing）故障占比应渐降（功能在补齐），冗余型（extraneous）可能缓升——缺失型回升 = 产品不稳定信号；冗余型突增 = 维护出了问题。
TERM · 核心定义
Root Cause Analysis（RCA）
根因分析：识别并消除过程故障的技术（源自核电工业）。四步：故障是什么（按严重度+种类分类，类别可演化）→ 何时发生/何时发现 → 为什么发生（把代表性故障层层回溯到「根因」，经验法则：连问六次为什么）→ 如何预防。与 ODC 的区别：RCA 聚焦少数最重要的故障类，ODC 比较多类趋势。
故障严重度分级（RCA 分类用）
级别描述示例
Critical产品不可用程序崩溃
Severe部分特性不可用且无变通办法无法导入旧版保存的文件
Moderate需变通办法，损害效率/可靠性/便利Postscript 导出不可用，可用打印替代但损失可用性与效率

考点 · Pareto 法则（80/20）与 RCA 追踪示例

20% 的代码贡献 80% 的故障——故障倾向聚集在少数模块，识别潜在问题模块可大幅提高检测的成本效益；少数故障类占主导，消除其成因对过程与产品质量影响巨大。回溯链示例（内存泄漏）：异常处理器忘记释放内存 ← 程序员难以确定清理什么（信息缺失）← 资源管理方案只考虑正常控制流（设计错误）← 根因：异常条件在设计后期才被想到。预防从轻量（设计评审清单加一项「异常条件」）到重量（需求分析与设计各步显式考虑异常）。目标不是完美，而是高性价比的改进——excellence is the enemy of the good。

许多高频故障类根植于过程与开发缺陷（浅层架构设计 → 资源分配故障；对开发环境不熟 → 异常处理故障），改过程/环境即可减少。改进多反馈到未来产品，有时能直接反馈进当前开发。

20.6质量团队的组织

质量计划必须把角色与职责分配给人：战略层（测试与分析策略、组织结构、外部要求如认证机构）与战术层（测试与分析计划）。战术层要平衡各时段工作量、管理人际互动、确保质量任务不被轻易忽略、鼓励对质量的客观判断（不被进度压力劫持）、培养共享的质量承诺与知识。

考点 · 外包测试的错误动机

「测试技术门槛低、可以交给低薪低技能的人」——错在混淆了测试执行（简单）与测试分析/设计（与设计和编程同样难）。正确动机：最大化独立性，降低成本只是副产品。计划必须定义外包活动的里程碑与交付、以及双向的交付质量检查。

  • 可复用资产：测试保存在仓库中，可复用、可改造；经验教训：改进资源配置与估算、测试技术创新、识别对用户数据的需求（含必要的隐私保护措施）。

LEARNING OBJECTIVES · 学习目标

  • 用图建模程序控制流

模型是「简化到刚好够用」的制品：四性质——紧凑（compact）、可预测（predictive，能区分好坏结果）、语义有意义（能诊断失败原因）、足够通用（够用于目标领域）。没有单一模型对所有分析都有用。

5.1图与控制流图（CFG）

有向图 = 节点集 N + 边集 E（N 上的关系）；节点可标注其代表的实体（如代码区域 x = y + z;）。

TERM · 核心定义
Basic Block 基本块 & CFG
基本块：只有单一入口点和单一出口点的最大程序区域。CFG 的节点 = 代码区域（常把语句合并成块以求紧凑；有时反过来把单条语句拆成多个节点以建模语句内控制流）；有向边 = 执行可以从一个区域的末尾直接进入另一区域开头的可能性。过程内的 CFG 也称 intraprocedural control flow graph。
示例 CFG：Java 方法 collapseNewlines（折叠连续换行符）——for 循环、if 条件与两个赋值构成的基本块及回边。图源：Lecture 05, slide 9

LCSAJ（Linear Code Sequence and Jump）：CFG 中从一个分支到另一个分支的子路径序列（Entry→b₁b₂b₃→jX 等），本质是「从一个跳转到下一个跳转」的直线代码段。

5.2调用图：过程间的近似

  • Call graph：节点=过程（方法、C 函数…），边=调用关系——过程间控制流图的基础。
  • 静态调用图高估调用关系：包含经动态绑定而实际从不发生的调用。例：C.cFactory("S") 返回子类 S 实例，静态图包含 C.foo() 与 S.foo() 两条边，运行时只走 S.foo()。
  • 上下文不敏感（context-insensitive）：每个过程一个节点，foo(3) 与 bar(17) 都汇入同一个 depends——快但混淆调用来源。
  • 上下文敏感（context-sensitive)：按调用上下文复制节点（depends(int,a,2) 与 depends(int,a,16) 分开）——代价是指数级增长：每层 if 分支使调用上下文翻倍（1→2→4→8→16……）。

5.3有限状态机（FSM）与抽象函数

FSM = 有限状态集（节点）+ 状态间转换集（边）。Mealy 机的表格表示：行=状态，列=输入（如 LF / CR / EOF / other），单元格 = 新状态/动作（如 e/emit、w/append）。

TERM · 核心概念
Abstraction Function 抽象函数
抑制程序执行的某些细节，把「仅在被抑制细节上不同、其余一致」的执行状态归并（lump together）为一个抽象状态。模型之所以有限，正因为抽象函数把无限的具体状态折叠成有限的抽象状态。
案例：C 函数 transduce()（行转换器）——抽象状态 e（空缓冲）/ w（行内）/ l（等待 LF）/ d（完成）对应具体状态（行号 × atCR × pos 的取值区间）；右侧为输入字符（LF/CR/EOF/other）驱动的状态转换表，每格「新状态/动作」。图源：Lecture 05, slide 18 · Pezzè & Young

用模型推理系统性质：三重信任

模型位于「性质」与「程序」之间，三重条件缺一不可：① 模型满足规格（Required Properties ⊨ FSM Model）② 模型语法良构、一致且完备 ③ 模型准确表示程序（FSM Model ≈ Program，如双检锁单例的并发行为）。任何一环断裂，模型的结论都不能转移到程序上。图源：Lecture 05, slide 17
考点

FSM 可在软件存在之前构建（记录预期行为、探索设计），也可从代码导出（抽象函数）；CFG 只能从软件构建。工具生态：状态图（statecharts，参见 statecharts.dev）以 FSM 为基础。

21.2集成故障的六种典型 + 一个真实案例

故障类型教材示例
参数/值的不一致解释火星探测器混用单位（米/码）——NASA Mars Climate Orbiter 事故

案例：Apache 2.0.48 的内存泄漏

HTTPS 端口上的普通页面请求：函数 ssl_io_filter_disable 只把指针置 NULL，缺了 SSL_free(inctx->ssl)。泄漏的结构在别处定义与创建、只能通过不透明指针访问——正常使用时缓慢泄漏，被用于 DoS 攻击时迅速耗尽。单元测试几乎不可能发现（模块本身行为正确，是跨模块的交互协议被破坏）；检视与某些动态技术本可以发现。

课堂吐槽 · 也许你听过

"Yes, I implemented ⟨module A⟩, but I didn't test it thoroughly yet. It will be tested along with ⟨module B⟩ when that's ready."（A 我写好了但还没细测，等 B 好了一起测就行。）

翻译过来就是：我完全没想过测试策略——没为可测试性设计 A，也没考虑 A、B 构建与测试的最佳顺序。集成测试不是单元测试的兜底。

21.3集成策略：从大爆炸到关键模块

集成测试计划与项目构建计划互相驱动，二者都源自系统架构——这是架构与项目计划的关键特征。

TERM · 核心定义
Driver / Stub
系统中一个模块会被「要求做事」，也会「要求别的模块做事」。测试单个模块时两者都未必存在，于是需要：驱动（driver）——代行上层模块对被测模块发出的调用；桩（stub）——近似模拟被测模块所调用的下层模块的行为。
驱动与桩：Driver 在上方调用「Module Under Test」，Stub 1 / Stub 2 在下方被其调用——分别替代「还缺的上下文」与「还缺的下层」。图源：Lecture 21, slide 16
集成策略一览
策略方向/依据脚手架要点
Big Bang 大爆炸全部集成完再测不需要「绝望之举」：可观测性/可诊断性/反馈最差、修复成本最高——唯一的借口（还很差）是不用搭脚手架
Top-down 自顶向下结构：从顶层沿「使用」关系向下桩（下层未就位）若从顶层界面（GUI/CLI/Web）驱动则无需驱动；逐个用真模块换桩，测试越来越彻底
Bottom-up 自底向上结构：从「使用」层次的叶子开始驱动（上层未就位）永不需要桩；真模块逐个取代驱动；叶子层可并行分多个子系统推进
Sandwich 三明治结构：从两端向中间更少结合自顶向下与自底向上，驱动与桩都可减少
Thread 线程功能：若干模块组成一个用户可见功能可减少一条线程一条线程地集成，最大化对用户的可见性
Critical module 关键模块风险：先做最危险的模块视情况风险评估先行（技术风险/过程风险）；战术上类似线程或三明治；集成测试 = 尽早送出坏消息的风险削减活动
自顶向下：主模块就位，为子模块 11、12、2、3 准备桩。图源：Lecture 21, slide 17
自底向上：从叶子模块开始，用驱动模拟上层调用者，逐层替换。图源：Lecture 21, slide 18
考点 · 如何选策略

功能导向策略（线程/关键模块）需要更多规划，但在复杂系统中提供更好的过程可见性；结构导向策略（自顶向下/自底向上/三明治）更简单，适合较小的组件与子系统。可以组合：小规模用结构策略，较大子系统常用线程 + 关键模块的组合。

21.4基于构件的测试

TERM · 工作定义
Component 构件
可复用的部署与组装单元：被多次部署、多次集成（通常由不同团队）；生产者 ≠ 使用者；以接口或契约为特征——描述访问点、参数、全部功能与非功能行为及使用条件；通常拿不到源码等其他访问途径；粒度常大于对象或包（一个完整的数据库系统可以是构件）。相关概念：框架=应用的骨架/微架构（可打包为带「钩子/插槽」的构件）；设计模式=逻辑设计片段（框架是具体的，模式是抽象的）；构件系统=主要由（常为 COTS 商用现成）构件组装 + 应用专属胶水代码。

接口契约比 API 签名大得多：API 与实现分离（如 XML 的 DOM 接口有多种实现）；契约包含使用构件所需知道的一切——非功能特性（性能、容量、安全）以及对其他构件的依赖。

  • 构件开发者的挑战：不可能预知构件的所有用法；难以识别并规格化所有重要性质与依赖；
  • 构件使用者的挑战：构件内部不可见；难以判断对特定用途与上下文的适配性。
构件测试：生产者视角 vs 使用者视角
生产者视角使用者视角
首要目标彻底的单元/子系统测试（含基于 API 的彻底功能测试）不是找构件的故障，而是回答「它适配这个应用吗？」
方法基于预期使用场景的彻底验收测试；含压力与容量测试关注适配风险：未预期的依赖/环境交互、性能容量上限、功能缺失或 API 误解
经验法则可复用构件在设计、实现、测试上的投入至少是一次性子系统的两倍；找出并文档化适用边界风险在使用首次时最高 → 尽早试验性集成：远在正式集成前就写驱动测试典型场景

应用常通过适配器（adaptor）访问构件——测试驱动（或访问桩的标准途径）同样可以走这个适配器，让「为测试留门」成为架构的一部分。

10.1为什么不用随机测试？

Random vs Systematic
方式做法问题 / 优势
Random（均匀）等可能地抽取输入避免设计师偏差（同一人设计程序与测试会犯同样的错）——但把所有输入当作同等有价值
Systematic（非均匀）选「特别有价值」的输入，通常是容易失败或根本不会失败的类的代表功能测试属于系统性测试

失败在输入空间是稀疏的——针在大干草堆里。例：求二次方程根的 Java 类 roots，实现逻辑不完整：未正确处理 b²−4ac = 0 且 a = 0；失败取值在输入空间极稀疏，随机采样几乎不可能恰好抽中 a=0.0 且 b=0.0。

考点 · 何时该用随机？

取决于测试目的：估计针的比例（可靠性估计需要无偏样本做有效统计）→ 随机；找出针并移除 → 系统性搜索。除非针很多，随机采样找针低效；要利用一切关于针的知识（更重？会沉底？）来设计搜索。

划分原理（The Partition Principle）

失败在整个空间稀疏，但可能在某些区域稠密。若某故障导致的失败在某个输入类中稠密（易找到），则从每类采样至少一个输入即可揭示该故障。这一理想情形很少保证——依赖经验性启发式。Quasi-partition：各类的并覆盖整个空间，但类可以重叠。功能测试就是「画粉线把大干草堆切成小堆，在针可能集中的小堆里系统性翻找」。

保险系统测试模型：输入处理 / 内部处理 / 输出处理三段等价划分，年龄输入分有效/无效类，对应接受、拒绝、超额警告等输出。Lecture 10, slide 10

测试基础：「extend 功能生成新路径，或生成失败」——接受路径 r 与点 p，返回端点为 p、倒数第二端点为 r 之端点的新路径 r′，条件是：r 端点到 p 距离不过长、且跨越步不穿越禁飞区；否则报错。测试完成准则：100% 等价类覆盖且全部通过。练习：找出等价类（环境含禁飞数据库），仿照保险例子画分区图，写出测试用例规格与具体测试。

10.2四步法：从规格到测试用例

① 分解规格 → 独立可测特性→② 选代表值 / 代表行为→③ 组合成测试规格→④ 生成并执行具体测试

  • 正确邮编：对应 0 个 / 1 个 / 多个城市；
  • 畸形邮编：空串；1–4 位；6 位；超长；含非数字字符；非字符数据。

规格即划分线索：roots 程序的规格本身就暗示了 0 / 1 / 2 个实根的划分——测试每一类以及类间边界；经验表明失败常落在边界上。

基本思想：识别数据/环境/配置中可独立变化的属性（如浏览器 × 操作系统），系统性地生成组合——要「多样」并覆盖 corner cases。三种方法解决三个痛点：手工选值、组合爆炸、经验复用。

11.1Category-Partition（分类划分测试）

核心分工：手工识别刻画输入空间的值（创造性步骤） + 自动生成组合（机械步骤）。三步流程：

Step 1 分解规格 → 特性/参数/环境元素 → 分类 (categories)→Step 2 为每类识别值 (choices)→Step 3 引入约束 (constraints)

案例：check-configuration（检查计算机配置）

参数 Model（型号：必选槽/可选槽数量决定约束）与 Set of Components（槽-组件对；组件间可互不兼容，如 RodentOS 移动服务器版要求 ≥30GB 硬盘）；环境元素 Product database。

  • Step 1 选分类没有硬性规则——反映测试设计师对「哪些值类可能被实现区别对待」的判断；需要领域与架构知识，要看出规格表面之下的隐藏特征（如 #DBM 数据库中型号数、槽数等）。
  • Step 2 值的来源：边界值测试（类内极值、类外紧邻值、类内内部值）+ 错误条件测试（正常域之外的值）。例：Model number ∈ {Malformed, Not in database, Valid}；#SMRS ∈ {0, 1, Many}；0 和 1 是特殊值，可能单独或与其他参数组合引发未预期行为。
  • Step 3 约束（关键省钱步骤）：全部组合 314,928 个，大多不可能（如「0 槽」配「至少一个不兼容槽」）：
三种约束把 314,928 个用例缩到 69 个
约束语义效果
[error]错误值类只需试一次（假设处理错误会绕过其余逻辑）314,928 → 2,711
[property] [if-property]把单参数的值按性质分组，限制跨参数可组合的值2,711 → 908
[single]非错误但只想测一次的值类（如 some default）908 → 69
考点 · single vs error

两者效果相同（都只测一次），但理由不同：error 是「错误处理绕过其他逻辑」的假设，single 是纯粹的数量控制。分开记录对文档与回归测试很重要——语义不同的约束，回归时的处理也不同。

11.2Pairwise（成对组合测试）

分类划分适用于直觉约束能把组合压小的场合；约束少时组合数失控。Pairwise：不穷举，而是高效覆盖所有值对（n-way 覆盖三元组…）。理由：大多数非预期交互只涉及两个或少数几个参数——覆盖对（三元组…）能以少得多的用例揭示大部分故障。

显示控制例子：3 × 4 × 3 × 4 × 3 = 432 全组合 Display Mode × Language × Fonts × Color × Screen size——全部成对组合只需 17 个测试用例

带约束的处理：简单约束（monochrome 与 laptop/full-size 不兼容）可分表处理——手持屏一张表、大屏一张表，各表内做 pairwise。注意：成对覆盖不会导致乘法式增长，但类多了手工做不动，需工具（如正交表 / IPOG 算法类工具）。

11.3Catalog-Based（目录驱动测试）

解决「Step 1–2 太靠个人经验」：把组织/领域的测试设计经验沉淀成目录（catalog）——每种可能的变量类型列出重要取值，加速设计、例行化决策、加速培训、减少人为失误。

整数变量目录：L−1 · L · 区间内部值 · U · U+1下界前一元素 / 下界 / 内部 / 上界 / 上界后一元素

三步流程：① 分析规格找出简单元素（pre-conditions、post-conditions、definitions、variables、operations）→ ② 从前置/后置/定义导出初始测试规格 → ③ 顺序扫描目录补全并删除冗余。

案例：cgi_decode（完整走一遍）

功能：把 CGI 编码串还原为 ASCII——+ 映射为空格、%xy（x,y 为十六进制位）映射为对应 ASCII 字符、字母数字原样复制；成功返回 0，输入畸形返回 1。

  • Step 1 元素：PRE1（假定：null 结尾）、PRE2（已验证：CGI 项序列）、POST1–6（复制/替换/返回值）、VAR1–3、DEF1–3（十六进制字符范围、%xy、CGI 项）、OP1（Scan encoded）；
  • Step 2 初始测试：简单前置条件 → 满足/不满足两类；复合前置（AND/OR）→ 应用 MC/DC；假定前置只对「OR 前置」用 MC/DC；条件型后置当作已验证前置处理。如 TC-PRE2-1/2、TC-POST1-1/2……
  • Step 3 目录扫描：Boolean（true/false，已被覆盖）→ Enumeration（每个枚举值+集合外值 → 生成 TC-POST5-2/3/4：以 %x 结尾、%ky、%xk）→ Range（十六进制位：'/'、':'、0、9、@、G、A、F、}、g、a、f 及内部值 → 30 个新用例）→ Constant（+ 与 %，全冗余）→ Sequence（空、单元素、多元素、超长、错误终止……6 个非冗余）→ Scan（P 在开头/中间/结尾、PP 连续、不出现、前缀陷阱……17 生成 10 非冗余）。
考点

目录法精髓：从规格的语法元素反查目录，让「想取值」变成「查表+去冗余」。最终 cgi_decode 得到约 70 个测试用例规格——数量可观但每一条都可追溯到规格元素或目录条目。

12.1为什么需要结构测试？

  • 回答「测试套件缺什么」：某段代码没被任何用例执行 → 其中的故障无法暴露。「部分」通常指控制流元素：语句（CFG 节点）、分支（CFG 边）、条件、路径；
  • 与功能测试互补：功能规格看不见的地方（一条规格由多段代码实现——哈希冲突处理）；
  • 无保证：执行了所有控制流元素 ≠ 找到所有故障——执行出错语句不一定破坏状态（取决于数据），破坏了状态也不一定传播到失败。

实践套路

先做功能套件，再测结构覆盖找缺口；解读未覆盖元素：可能是规格与实现的自然差异，也可能是规格不完备、编码严重偏离规格、功能套件不足。覆盖率自动化方便，常被当作完成判据——慎用：不保证套件有效。

12.2从语句到分支

Statement Coverage = 已执行语句数 ÷ 语句总数基本块（basic block）覆盖 / 节点覆盖与语句覆盖：100% 时等价，100% 以下数值不同但方向一致

案例 cgi_decode（C 版）：用例组 T₀ = {"", "test", "test+case%1Dadequacy"} 达 17/18 = 94%；T₂ = {"%3D", "%A", "a+b", "test"} 达 18/18 = 100%。覆盖 ≠ 规模：T₁ 覆盖高于 T₀ 但基数更小；小套件诊断更容易——最小化套件很少是目标。

100% 语句覆盖可能漏分支：若 else 分支 F 缺失（T₃ = {"", "+%0D+%4J"} 达 100% 语句覆盖但 D→L 的假分支从未走过）→ 需要 Branch Coverage：

Branch Coverage = 已执行分支数 ÷ 分支总数T₃: 100% 语句 + 88% 分支 (7/8)；T₂: 100% + 100% (8/8)
考点 · 蕴含与不蕴含

遍历所有边必经过所有节点 ⇒ 分支覆盖 subsumes 语句覆盖；反之不成立（T₃ 即反例）。

12.3条件测试与 MC/DC

分支覆盖只检查「程序员把计算分解成情形」的大框架，把同结果的情形归并了。故障例子：digit_high == -1 || digit_low == -1 漏写取反（应为 digit_high == 1）——只变 digit_low 就能同时满足分支覆盖，坏的那个子表达式从未真正影响过结果。

12.4路径类准则（实用化）

  • Path adequacy：每条路径至少执行一次——含循环的程序路径数无界，通常不可满足；可行做法是把无限路径集划分成有限类：限制循环遍数、路径长度、路径间依赖。
  • Boundary-interior path testing：沿 CFG 追到第一个重复节点为止的子路径集合（把循环体内差异的路径归并）。局限：N 个顺序 if 仍产生 2ᴺ 条子路径；为特定路径构造输入可能极难（条件不独立时甚至不可能）。
  • Loop boundary adequacy：每个循环体执行 0 次 / 1 次 / 多次 各至少一个用例——对应循环正确性证明会考虑的情形。
  • LCSAJ（Linear Code Sequence and Jump）：从分支到分支的顺序子路径。TER₁=语句覆盖、TER₂=分支覆盖、TERₙ₊₂=n 个连续 LCSAJ 的覆盖。
  • Cyclomatic adequacy：圈复杂度 = CFG 的独立路径数；V(G) = e − n + 2（CFG）/ e − n + c（一般图）。度量已执行的独立路径数占圈复杂度的比例。

  • 边界条件：给每个递归产生式标注最小/最大应用次数，生成 min、min+1、max−1、max 四档。

9.2不可满足性与覆盖率

有时没有任何测试套件能满足某准则——例如防御式编程的「不可能发生」检查：if (z < 0) throw new LogicError(...)，若程序正确则该分支永不可达，语句覆盖不可能 100%。两种应对：

  • Approach A：从准则中剔除不可满足的义务（修改语句覆盖为只要求「可执行」语句）——但我们无法确知哪些可执行（不可判定！）；
  • Approach B：度量接近准则的程度——满足 100 个义务中的 85 个 = 85% 覆盖率。准则满足与否是布尔值；覆盖率度量是分数。
考点 · Coverage: Useful or Harmful?

覆盖率是有用的进度指标（离彻底还有多远、哪里是薄弱点），也是危险的诱惑——它只是彻底性的代理：提升覆盖率数字比设计好测试容易得多。唯一真正重要的度量是（成本）有效性。类比建筑规范（building codes）：达到规范 ≠ 好房子，但违反规范足以让你警惕；规范有时过严，可豁免但需满足其他要求。

9.3比较准则：Subsumes 关系

TERM · 核心定义
A subsumes B（A 包含 B）
当且仅当：对每个程序 P，每个满足 A（关于 P）的测试套件也满足 B（关于 P）。例：分支覆盖 subsumes 语句覆盖。

两种比较路径：经验法（研究工业实践中不同测试方法的有效性——最重要，但依赖情境、难泛化）与解析法（证明一个准则在何种条件下严格强于另一个——subsumes 是其中之一，只是整体「有效性」问题的一块拼图）。用途：从易到难逐级工作；不是质量的直接指标。

准则的两大用途

  • 测试选择：指导设计彻底的测试套件（如基于规格的准则提示覆盖代表性取值组合）；
  • 事后分析（post hoc）：揭示可能遗漏了什么——典型组合拳：先按规格设计功能测试，再用结构准则（如分支覆盖）照亮遗漏的逻辑。

Ch 16变异测试种子缺陷等价变异体
LEARNING OBJECTIVES · 学习目标

一个弹珠思想实验贯穿全讲：往一碗弹珠里混入 100 颗黑色弹珠、搅匀、随机抽 100 颗、其中 20 颗黑——可以估计碗中原有多少弹珠。把「程序」与「种子缺陷」代入这个公式，就是变异测试。

16.1用种子缺陷评估测试套件

把 100 个新缺陷（假设与真实缺陷各方面都一样）逐个植入程序的 100 个副本，跑测试套件：揭示 20 个 → 推断套件对同类真实缺陷的检出率约 20%。有效性取决于种子缺陷对真实缺陷的代表性——不必完全相同（黑弹珠 ≠ 透明弹珠），但差异不能影响「选择」：若混入钢珠再用磁铁捞出，你对碗里有几颗弹珠一无所获。

TERM · 核心定义
Mutant / Mutation / Killed
变异体（mutant）：带一个变异的程序副本；变异（mutation）：一处语法改动（植入的缺陷），如把 (i < 0) 改为 (i <= 0)；变异体在至少一个测试用例上失败即称被杀死（killed）。杀死大量变异体 → 推断套件对真实缺陷也有效。

两大基本假设（必须能复述+批评）

假设内容
Competent Programmer Hypothesis
胜任程序员假设		程序接近正确，真实缺陷只是正确程序的小变异 ⇒ 变异体是真实缺陷程序的合理模型
Coupling Effect Hypothesis
耦合效应假设		能发现简单缺陷的测试也能发现复杂缺陷 ⇒ 即使变异体不完美代表真实缺陷，杀变异体的套件也擅长抓真缺陷

16.2变异算子与存活变异体

变异算子 = 从合法程序到合法程序的语法改动，与语言绑定（C++ 的算子不能用于 Java/Python）。三例：

  • crp（constant for constant replacement）：把 (x < 5) 改成 (x < 12)，新常数取自程序文本中出现的常数；
  • ror（relational operator replacement）：(x <= 5) → (x < 5)；
  • vie（variable initialization elimination）：int x = 5; → int x;。
考点 · 存活变异体的两种解释

100 个变异体杀死 94 个、存活 6 个——每个存活者只有两种解释：① 等价变异体（equivalent mutant）：改动根本不影响输出，「假缺陷」，判定等价性在最坏情况下不可判定；② 套件不足：本可杀死却没杀。陷阱题：「为这个存活变异体加一个测试」是错误策略——我们在乎真实缺陷，不在乎假弹珠！正确姿势：分析存活者暴露的模式，改进整体测试设计。

16.3两种省钱的变体

问题：变异体数量随程序规模平方级增长，逐个跑完太贵。

变体做法
Weak mutation
弱变异		运行「元变异体（meta-mutant，植入多个缺陷）」与原程序同步执行，一发现中间状态差异立即标记该缺陷被杀死，不必等程序跑完；每次 kill 后换新的变异选择重启
Statistical mutation
统计变异		只随机抽样一部分变异体——评估套件同样够用；前提是不能为杀特定变异体而设计测试（那等于专挑黑弹珠，统计失效）

现实地位

  • 半导体制造业的成功先例：良好的制造故障模型（如晶体管 stuck-at-one），但设计错误的故障模型（软件的情形）难得多；
  • 工业界不普遍使用变异测试，但它是测试研究中比较技术有效性的标准手段；
  • Stryker（JS）、Mutatest（Python）、PIT（Java）等工具正使其更易落地；
  • 用故障模型设计测试这件事本身重要且被广泛实践（区别于「跑变异体」）。

22.2系统测试

关键特征：覆盖全面（整个系统、整个规格）；基于可观测行为的规格——是对需求规格的 verification，不是 validation、不是个人意见；独立于设计与实现——避免把软件的设计错误复制进系统测试设计。

  • 不换人也能提升独立性：尽早开发系统测试用例——作为需求规格的一部分，在重大设计决策之前；敏捷 test-first 与传统 V 模型都是「先设计系统测试、后设计实现」的例子；也是 design for test 的机会；
  • 增量式系统测试：系统测试套件覆盖全部特性与使用场景，随项目推进通过的用例越来越多 → 成为进度度量；前提是「线程式」增量构建计划；
  • 全局属性：性能、时延、可靠性等本质上全局——早测/增量测只能给出估计；系统测试是对照实际系统规格验证全局属性的唯一机会，尤其用于发现未预期效应（如意外的性能瓶颈）。
考点 · 上下文依赖属性 与 运行包络

有些属性取决于系统上下文与使用方式：性能取决于环境与配置；隐私既取决于系统也取决于使用方式（医疗记录系统既要防未授权访问，授权又只能按需给）；安全取决于威胁画像——而威胁会变！测试只是应对的一部分。当属性随使用参数化（每秒请求数、数据库规模……），就要做极限/压力测试：在包络内、边界附近、以及超出边界系统性地变参，目标是得到「属性如何随参数变化」的良理解模型——敏感度如何？包络的边缘在哪？超出包络会怎样？压力测试常需大量模拟执行环境、消耗比常规用例更多人力机器——与常规特性测试分开、低频执行、手动控制多，还要诊断与预期的偏差（可能牵出潜伏故障的艰难调试）。

22.3验收测试：用统计估计依赖性

验收测试在度量质量，而不是搜寻故障——与系统化测试目标根本不同。定量的依赖性目标是统计量（可靠性、可用性、MTTF），需要从运行剖面（operational profile）抽取有效统计样本：

  • 有效的运行剖面：来自旧版本系统，或运行环境（嵌入式控制器）；敏感性测试揭示哪些参数重要、哪些可以粗略估计；
  • 对被测对象的清晰精确定义：故障率按会话、按小时还是按操作计？（呼应 L01 的「可靠性取决于度量单位」）
  • 大量的随机样本——可靠性要求越高，所需样本越多。
考点 · 统计测试值得吗？

安全关键系统、基础设施等必需；但当运行剖面拿不到或只是猜测（常见于涉及人机交互的新功能）时很难做——可把关键功能从整体使用中剥离、只为关键性质建模；可靠性要求极高时，所需样本量可能要几年的测试执行——超可靠性几乎无法靠测试证明（ultra-reliability can seldom be demonstrated by testing）。

基于过程的度量（不如统计测试严格）：依靠与既往项目的相似性。系统测试过程有「预期的故障发现-解决史」；Alpha 测试（真实用户、受控环境）与 Beta 测试（真实用户、真实不受控环境）——可以按用户而非按使用抽样；同样有预期的故障报告史。

22.4可用性与可访问性

可用的产品：学得快、让用户高效工作、用得愉悦。客观判据：完成任务的时间与操作数、用户出错频率（把用户错误归咎于产品！），加上整体的主观满意度。

可用性的分解：validation 定标准，verification 查落实
Validation（可用性实验室）Verification（开发者、测试者）
做什么可用性测试建立可用性检查清单（适用于产品线/领域）；早期用「纸板原型/样机」做可用性测试 → 产出界面设计检视把可用性检查清单应用到规格与设计；行为对照界面设计被客观验证（如测试）
意义把可用性测试「因式分解」进过程可见性：validation 建立的判据，由整个项目周期的 testing / analysis / inspection 来 verification
  • 三种可用性测试：探索性（研究用户心智模型，早期指导界面设计）、比较性（评估具体界面选项，观测并度量不同交互模式）、可用性验证（整体定量+定性评估：出错率、完成时间）；
  • 典型测试协议：从 1–4 个用户群各选 3–5 名有代表性的用户（问卷核验群组归属）→ 请其执行有代表性的任务序列 → 只观察不干涉（对开发者最难的是不出手帮忙；专业可用性测试用单向镜）→ 度量（点击、眼动、时间……）+ 事后问卷；
  • 可访问性测试：残障人士（盲/低视力、聋、色盲……）的可用性。直接对全部相关人群做可用性测试通常不现实——对照可访问性指南检查是可行的且常能暴露问题，如 W3C WCAG（Web Content Accessibility Guidelines）：部分可自动检查，但仍需人工检查（如图片的 alt 标签是否有意义）。

22.5回归测试

"Yesterday it worked, today it doesn't." —— 修 X 时顺手弄坏了 Y；那个 bug 修好了，现在又回来了。任何变更后都要重跑测试：加新功能、适配新环境、修复其他 bug。回归测试可能是软件维护的主要成本——有时远超做变更本身。

回归测试的两大基本问题
问题内容与对策
测试套件的维护特性 X 变了 → 用到 X 的用例要改（不可避免的维护）；但琐碎的界面/文件格式变更不应作废大量用例（应避免的维护）→ 套件要模块化、避免不必要的耦合；从测试用例规格生成具体用例可有帮助
重测的成本常与产品规模而非变更规模成正比；手动测试时是大问题；自动化也有问题——套件与执行时间增长到超过几小时就麻烦
TERM · 一对易混概念
Obsolete vs Redundant Test Case
过时用例：不再有效（测的是被修改/替换/移除的特性），应从套件移除；冗余用例：与别的用例无显著差异，不太可能发现被相似用例漏掉的故障——重执行有人力机器成本、维护有人力成本（往往更高），视成本可删可留。

选择 与 优先级

要整个套件重跑吗、按什么顺序？若午休时间就能全自动重跑，不用纠结。选择在用例昂贵时重要（专用设备、长运行时间、无法全自动）；优先级在超大套件无法每天跑完时重要。四条路线：

路线机制
基于代码的选择观察：用例不可能在它不执行的代码里发现故障 → 只重跑覆盖了改动/新增代码的用例
控制流/数据流选择同一思路的结构化版：改动元素=控制流节点与边、或数据流的 def-use 对；工具记录每个用例触及的元素（存入回归用例库），标记程序变化，查重叠
基于规格的选择挑测试新增/变更功能的用例；但不保证独立性——不是「为 X 而写」的用例也可能发现 X 的 bug → 典型做法是优先级：全跑，但变更相关的先跑
优先轮转 prioritized rotating最终跑完一切、只是有先有后：轮转（最久未跑的优先）、战绩（以前发现过故障的优先——它们大概执行了高故障密度代码）、结构（最久未被执行的元素优先；可粗粒度到特性/方法/文件）

23.1自动化的角色与三维评估

自动化扮演四种角色——判断一个工具属于哪一种，是评估的第一步：

Potential Roles of Automation
角色含义与例子
引入任务的必要条件没有工具这任务根本做不了——如覆盖工具使「度量测试套件的结构覆盖率」成为可能。
降低成本捕获-重放（capture & replay）工具大幅降低重新执行测试套件的成本。
提升（人的）生产力软件检查（inspection）本身是手工活动，但组织与呈现信息、管理沟通的工具能提高人的效率。
CI/CD 的本质前提持续集成/部署的每一步都须自动触发——没有自动化就没有 DevOps。

三个（不正交的）评估维度：① 活动的价值与当前成本；② 活动在多大程度上需要自动化（或能被自动化变得便宜）；③ 获取或构建工具的成本。再叠加技术的影响、成熟度、成本与范围，以及与组织和过程的契合度，决定自动化的优先顺序。

考点 · 自动化成本的两极

有些工具简单到收益平平也值得做——如「从 FSM 模型生成测试用例」；有些工具价值巨大却原理上不可能——如精确识别「永不可执行的代码」（不可判定问题）。范围也影响成本：通用工具（如面向所有 Windows 应用的捕获-重放）只比项目专用版贵一点，投资可跨项目摊销；大项目里自建工具（如让各子系统能独立测试的模拟器）常是好投资。

聚焦自动化最划算的地方：简单重复的任务——人做重复任务既慢又易错；而判断与创造性问题求解留在自动化范围之外。人极擅长识别「对应测试用例规格的相关执行场景」，却极不擅长批量生成用例、或在回归测试的海量输出里找出错误结果。把任务中重复的部分自动化，降本的同时还提高准确性。

23.2过程管理中的自动化：计划与监控

策略层 vs 项目层

  • 策略层（strategy）：为质量过程的关键环节规定工具，可按项目特征（应用领域、语言、规模、质量要求）推荐不同工具。常入策略的：组织测试设计与执行、生成质量文档、收集度量、管理回归套件；较少入策略的：测试用例生成、动态分析。
  • 项目层（project）：A&T 计划列出继承自策略的工具 + 本项目增选的工具；新增/定制工具必须写清成本（含培训）、隐含活动、潜在风险，并把工具安放进开发过程与方法论。反例：覆盖率工具便宜简单，但若不与用途结合，就只是产出无人使用的数据的烦扰。

经典计划工具与配置管理

经典计划工具按资源与时间约束排任务，可特化为 A&T 管理：识别某产物已交付 → 调度对应测试套件执行 → 把结果通知测试设计者 → 记录活动实际耗时 → 向质量经理标记进度偏离。版本与配置管理工具把大量产物的版本关联起来，触发一致性检查——例如每次软件修改自动触发相应测试套件重跑；但它们提升的是良序过程的效率，不能替代组织本身。监控同理：集成质量追踪改善良序过程的效率，无法让混乱自行变有序；进度要看日程（实际工时与完成时间 vs 计划）与质量水平两条线。

代理度量：LOC 与检出故障数

最终产品的质量在完成前无法直接测量，只能用代理度量（proxy measures）尽早捕捉偏离期望——必须早算，且解释方式要避免误导结论或扭曲激励：

  • 代码行数 LOC：生产力的粗糙代理——解读不当会同时制造「鼓励啰嗦」与「打击有效复用」的扭曲激励；
  • 检出故障数：偏离常态的信号——异常低与异常高同样值得警惕（低可能意味着没在找，高说明过程有病）；
  • 数据的收集、汇总、呈现可以自动化；设计与解读不能（正交缺陷分类 ODC 见 L20）。

管理沟通

软件工程师的大量时间花在沟通上；通用工具（邮件、聊天、论坛）要在同步与异步之间求平衡：打断过多拖慢进度就转异步；交流碎成许多小段、总在等回复就转同步。沟通在各方即时可及相关信息时最有效——任务专用工具（如分布式评审工具：受管理的产物呈现 + 对应检查单片段 + 自动分析结果）能进一步提效。

23.3度量：尺寸、复杂度与圈复杂度

度量进展与结果是管理过程的必需品，但我们真正关心的（对目标的实际进展、剩余工作量、预期可靠性…）往往测不到——所以一切度量都是需要按本地条件校准的代理。静态度量中最基本的是尺寸：与日程和成本强相关；粗颗粒计数（模块、接口、函数、形参）也常用，而更精巧的度量在判断工作量上并不比 LOC 更好（或更糟）。

圈复杂度 Cyclomatic Complexity

直觉：若能度量程序（或其部件）有多复杂，就能把测试与分析聚焦到最易出错的部位、做出更好的计划、或考虑重构过复杂的子系统。但真正的逻辑复杂度无法直接度量——控制流复杂度是代理。在众多复杂度尝试中，只有圈复杂度沿用至今：

V(G) = 控制流图中独立路径的条数 = e − n + 2e = 边数，n = 节点数（edges − nodes + 2）

23.4测试生成、执行与静态分析的自动化

测试用例的设计与实例化执行占整体 A&T 成本的大头，临近交付时还会成为调度瓶颈。设计测试套件需要人的创造力；而实例化与执行是重复且乏味的任务，可以大幅自动化——降本的同时加速测试循环。三个阶段要领：

  • 把创造性工作尽量前推：如把功能测试套件的设计当作规格过程的一部分——从系统需求、架构接口到模块接口，逐级进行；
  • 与产品一起建造脚手架（scaffolding）；
  • 自动化实例化与执行——不让它成为瓶颈，且可反复执行多次。

静态分析与证明

  • 快速廉价的简单性质检查：如数据流分析识别异常模式；
  • 关键性质所需的昂贵检查：如用有限状态验证工具找同步故障；
  • 为验证而设计（Design for Verification）：分解验证问题——设计上把安全关键性质封装进一个小的安全内核（safety kernel）；验证上对内核证明安全性质，再便宜地自动检查所有安全相关动作都经内核中介。
思考题 · THINK

"哪些工具会误报，哪些工具会漏报，哪些工具需要专家伺候？"

数据流分析器报异常模式，可能误报（false alarms）；bug finder 避免误报但可能漏检真实违例；模型检查器完全自动，但把模型与性质形式化通常要反复数轮；定理证明器需要强数学背景的专家交互引导选择证明策略——重量级工具的代价是「人的技能」。

简单分析工具只查固定的简单性质、无需额外规格：类型检查器（语法层面的良构规则，违例易诊断易修复，但规则常比希望的更严）、数据流分析器（对控制流与数据流敏感，识别的是异常而非明确故障）、领域专用检查器（如网站链接检查器）。复杂分析工具则分两档：基于定理证明的验证器（性质面宽、需大量人工交互）与有限状态验证工具（焦点受限、完全自动执行）。

  • 调试 ≠ 测试：测试=发现故障的存在；调试=定位、诊断并修复故障。两者常由不同的人负责。调试从测试用例出发——一个必然失败的小而简单的用例，远比一个时好时坏的复杂场景有价值；大量单一用途的小用例胜过少量综合性的大用例。

24.1为什么写、写哪三类

目的：监控与评估过程（对内：过程可见性；对外：认证、审计）；改进过程（维护跨项目复用的知识体、汇总数据供过程改进）；提升测试套件等制品在项目内外的可复用性。三大类文档：

类别内容
规划类 Planning描述质量过程的组织方式：组织级策略、项目计划
规格类 Specification描述测试套件与测试用例（及其他质量任务制品）：测试设计规格、测试用例规格、检查清单、分析过程规格
报告类 Reporting分析与测试结果的细节与汇总

元数据（便于管理）：批准人（对文档负责的人）、文档历史、目录、摘要（相关性与可能的用途）、目标（谁该读、为什么）、所需文档与引用（理解与利用本文档所需的制品）、术语表。命名规范帮助快速识别文档，典型命名包含：总体范围（项目与部分）、文档类型、具体标识、版本：

24.2关键文档逐个看

  • 测试与分析策略（组织级）：为一组项目（通常是整个公司）描述质量指南；要素：跨产品的公共质量需求——取决于业务条件（安全关键厂商须满足认证机构规定的最低依赖性；嵌入式部门须保证跨产品线可移植）；对其他质量文档提出要求；
  • 测试与分析计划（项目级）：标准化结构；总体质量计划由若干个体计划组成，每个指明待验证项（待检视的文档、待分析/测试的代码……）；可面向整个系统或子系统/一组单元；可以不覆盖质量活动的所有方面，但必须写明被排除的特性——遗漏测试是大项目失败的主因（GUI 计划只管功能、不管可用性——因为另有团队负责——可以，但要写出来）；
  • 测试设计规格：与其他设计文档同目的（指导后续开发、为维护做准备）；描述完整的测试套件，可按粒度分（单元/集成/系统/验收）或按目标分（功能/结构/性能）；包含初始选择测试用例与长期维护套件所需的全部信息：待验证特性（交叉引用规格/设计文档）、测试过程与通过/失败判据（引用脚手架与预言）、（逻辑上的）用例清单；
  • 测试用例规格：单个用例的完整设计——定义测试输入、所需环境条件、执行过程、期望输出；指明被测项（引用设计文档）、对其他用例执行的依赖；唯一标识；
  • 测试与分析报告：服务于开发者（定位未解决故障、安排修复与修订）与测试设计者（评估并精化自己的方法，呼应 Ch20）；核心是按优先级排列的未解决故障清单；失效报告必须整合、分类（系统性管理修复投入）、排优先级（合理分配投入、不遗漏）；
  • 汇总报告与详细日志：汇总报告跟踪进度与状态——可以只是「构建-测试循环成功运行」的确认，也可为关注点导航；汇总表包含：执行的套件、失效数量、失效的分解（先前已出现过的 / 新增 / 以前失败现在通过的）；可能由认证机构规定格式。

24.3「这么多文档，值得吗？」

值得，但有三个前提：

  • 手工产出的每样东西都要真的被用——永远知道文档的目的，绝不为没人用的文档花力气；
  • 能自动化的部分交给机器——人负责做决定并解释决定，其余交给机器；
  • 从用途倒推：从用途 → 输出 → 输入 反向设计；考虑组织与项目的特点；在最便宜、最省事的点上捕获决定及其理由，避免重复。
考点

文档可以被检视，以验证进度是否符合进度表与质量目标、识别问题——文档支撑过程可见性、监控与标准化，这正是它与 L20「可见性」的连接点。

27.2测试金字塔与 API 优先

测试金字塔（据 Sommerville Fig. 9.5 重绘）：底层数量庞大的单元测试全自动、成本最低；中层特性测试经 API 执行；顶层系统测试最少且最昂贵——「自动化程度递增、成本递减」沿箭头指向金字塔底部。图源改编：Lecture 27, slide 6
  • 为什么 API 优先：用户通常经 GUI 访问特性，但 GUI 测试的自动化很昂贵——应把系统设计成特性可经 API 直接访问，而非只有 UI 一条路。测试即可绕过 GUI 直达特性；额外收益是关注点分离：可以重实现 GUI 而不动功能构件。
  • 系统测试：验证系统需求、模拟用户行为，找特性间交互引发的问题、导致崩溃的动作序列。手工重复执行既枯燥又易错；动作时序有时至关重要、人工几乎无法一致复现——于是用录制-回放工具：录制 UI 手势，需要时自动重放，把重复劳动交给机器。

定义：先为代码写可执行测试、再写代码——测试即一种规格。由极限编程（XP）早期倡导者提出，但可用于任何增量开发方式；最适合单个程序单元，系统测试与 GUI 场景难以应用（连最坚定的倡导者也承认）。

27.4安全测试：风险驱动的样板

目标：发现可能被攻击者利用的漏洞，并提供「系统足够安全」的令人信服的证据——应能抵抗对可用性的攻击、恶意软件注入、以及对用户数据与身份的窃取与破坏。全面的安全测试需要漏洞与攻击方法的专业知识——但永远存在 unknown unknowns（未知的未知）。

典型安全危害（节选）

  • 未授权攻击者用合法凭据进入系统；认证系统未能识别攻击者；
  • 授权个人访问越权资源；或访问合法资源后外泄给未授权者；
  • SQL 注入（poisoning）攻击数据库；HTTP 会话管理不当；会话 cookie 泄露；
  • 机密数据未加密；加密密钥泄露给潜在攻击者。

类型使用一致吗？有类型系统的语言应遵守使用约定（如命名）
代码排版规范吗？避免混乱展示引发的常见阅读困难

27.6持续集成 Continuous Integration

「这个项目已经开发了两三年，目前正在集成——并且已经集成了好几个月。带我的向导说，没人知道还要集成多久。」——Martin Fowler：集成是漫长而不可预测的过程。CI 的解法是频繁集成：每次提交自动构建、自动跑全部测试，把集成从「不可预测的阶段」变成「每天都在发生的日常」。

持续集成 in GitLab：提交/合并请求自动触发流水线，构建、测试、报告一体化。图源：Lecture 27, slide 24
持续集成在 DevOps 中的位置：开发与运维的闭环里，CI 是每次变更的质量门禁。图源：Lecture 27, slide 25
CI Pipeline 流水线：阶段（stage）与作业（job）的自动执行序列；测试失败即阻断流水线——集成问题在提交当场暴露，而不是数月后的集成阶段。图源：Lecture 27, slide 26

本讲四句话总结：在人工交互价值低的地方尽量自动化；风险驱动的方法很有用（如安全测试）；评审与测试互补；如今已有相当完备的自动化工具链（如 GitLab）。

MEMO · 本讲速记
可执行测试输入+期望结果+检查；AAA=Arrange/Action/Assert；运行器跑全量出报告。
金字塔越往底部（单元）越自动、越廉价、数量越多；特性测试走 API 绕开 GUI；系统测试用录制-回放。

C4必背要点

  • 测试 vs 调试：测试暴露失效（failure）；调试定位并修复故障（fault）——目标是发现并消除故障（L01 · L23）。
  • 充分性准则：套件 T 满足 C ⟺ T 覆盖 C 规定的覆盖项集；subsumes 用于比较强弱，不是质量的直接指标（L09）。
  • 变异测试：变异得分 = 杀死变体数 ÷ 非等价变体数；等价变体不可能被杀死（L16）。
  • 组合测试：成对 pairwise 覆盖任意两参数的全部取值组合；base-choice 每次只变一个参数（L11）。
  • ODC / RCA：ODC=检出记录（活动/触发器/影响）+修复记录（目标/类型/来源/年龄）看趋势；RCA 聚焦少数关键故障，连问六次为什么，Pareto 80/20（L20）。
  • 可用性测试：每群 3–5 名有代表性的用户、只观察不干涉；可访问性对照 W3C WCAG 指南（L22）。
  • 统计测试：有效运行剖面 + 明确度量单位 + 大样本随机执行；超可靠性几乎无法靠测试证明（L22）。
  • 29119 五部分：1 概念定义 · 2 测试过程 · 3 测试文档 · 4 测试技术 · 5 关键字驱动；-3 三层文档：§6 组织级 · §7 管理 · §8 动态（L25/L26）。
  • 两条符合路径：完全符合（瀑布全量）vs 裁剪符合（风险驱动 · 敏捷示例）（L26）。
  • 发布门禁（敏捷）：高风险故事全 DONE + 残余风险 PO 接受 + SIT/UAT 全通过（L26）。
  • AAA 与金字塔：Arrange–Action–Assert；单元多而廉、系统少而贵、特性测试走 API（L27）。
  • TDD 循环：写失败测试 → 桩 → 实现 → 全绿 → 重构；测试即规格（L27）。
  • 评审检查清单五问：命名有意义？数据错误都测了？异常都处理？类型一致？格式规范？（L27）。
  • 圈复杂度：V(G) = e − n + 2 = 独立路径数；>20 复杂、>50 几乎无法彻底测试；只刻画控制流复杂度，不代表全部逻辑复杂度（L23）。
  • 自动化决策：角色四分（必要 / 降本 / 提效 / CI-CD 前提）× 三维评估（活动价值成本 · 依赖程度 · 工具成本）；重复任务自动化、判断与创造留给人（L23）。
